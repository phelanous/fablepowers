# Changelog

## 0.7.0 — 2026-10-17

fablepowers runs in Pi 1.x (`@earendil-works/pi-coding-agent`) from the same repository, with the same skills, seats, approval gate and workflow map. Claude Code, Codex and OpenCode behaviour is unchanged, apart from the security fix and the pending-creation fix below, which apply to every harness. Tested with Pi 1.2.0. Reasons and spike evidence are in `docs/rationale.md` (Decisions 2026-10-16: the Pi port).

- **Security fix, every harness: case-variant paths no longer slip past the gate.** The "inside the repository" check compared exact path prefixes, and `realpath()` does not canonicalise case. So on a case-insensitive filesystem, `<parent>/REPO/src/x` (or an NTFS name variant such as `repo.`) named a file in the repo `<parent>/repo`, but the gate treated it as outside and allowed the edit while a design was pending. This affected every harness since its gate shipped (Claude Code 0.4.0, Codex 0.5.0, OpenCode 0.6.0). A path under the toplevel only case-insensitively now counts as inside; the rest of it is compared exactly with `docs/specs/`, `docs/plans/` and `.fablepowers/`, so a variant spelling of those is denied too (fails closed; on a case-sensitive filesystem such a path is a sibling directory and is denied as well).
- **A spec created through a case-variant path still goes pending, on every harness.** The pending check compared `docs/specs/` exactly, so `<parent>/REPO/docs/specs/x.md`, `DOCS/Specs/x.md`, `x.MD` or `x.md.` created a design without arming the gate. The directory is now compared per component, case-insensitively and with NTFS normalisation, and the name counts as `.md` the same way; the key keeps its case and the spec path is recorded as written, under the toplevel. On a case-sensitive filesystem this can mark a stray file pending, the safe side; `/fablepowers:withdraw` clears it.
- **Installs on Pi as a package.** `pi install git:github.com/phelanous/fablepowers`, or `pi -e <checkout>` for one run. The root `package.json` gains `"pi": {"extensions": ["./pi/fablepowers.ts"], "skills": ["./pi/skills"]}`, and its `files` list gains `pi/` so an npm tarball carries the extension. The extension loads once per session generation: a second copy in the same process (a `-e` checkout plus the installed package) registers nothing and logs a line, and `/new`, `/resume`, `/fork`, `/reload` and RPC session switches register it again.
- **Skills as prefixed wrappers.** Pi skill names have no namespace, so `pi/skills/fablepowers-<skill>/SKILL.md` wraps each model-invocable skill (ten; approve and withdraw are commands). Each keeps the original description and points at `../../../skills/<skill>/SKILL.md`. `scripts/gen-pi-skills.sh` generates them, and a test fails when they drift from `skills/`. The prefix keeps them apart from a user's own skills and from superpowers' Pi skills of the same bare names.
- **Bootstrap on Pi.** A system-prompt section, `fablepowers_workflow`, set in root sessions only. Pi keeps it in every request and through compaction. It comes from the new `hooks/session-start --pi` mode, which never reads stdin and prints JSON (`context`, `seats`, `warnings`), run once per session with a 3 s timeout. The preamble names Pi, `references/pi.md`, the plugin root and the skill-name rule (`fablepowers:<x>` is `fablepowers-<x>`), then the seat table and its warnings, then the workflow map; at most 8,000 characters. Missing python, a failed session-start, or `FABLEPOWERS_PARENT_SESSION` without the child flag each add a first-line note.
- **Seats are pinned per user in `[pi]`.** In `${XDG_CONFIG_HOME:-~/.config}/fablepowers/models.toml`: `implementer`, `strict_implementer` and `reviewer` as `provider/model-id` (up to 128 characters, `@` allowed, no `:level` suffix), plus optional `<seat>_thinking` set to one of `off|minimal|low|medium|high|xhigh|max`. A bad thinking level warns and leaves Pi's default; `<seat>_thinking` without a pinned model and `<seat>_effort` warn and are ignored. An unset or invalid seat runs on the session's model and thinking level, with one warning line naming the unpinned seats. `[codex]` and `[opencode]` output is byte for byte unchanged, and each harness ignores the others' tables.
- **`fablepowers_dispatch`, a dispatch tool derived from Pi's MIT subagent example.** `{seat, task, cwd?}`, sequential. Each call runs the parent's own Pi executable as a child (`--mode json -p`, `-e <plugin-root>`, `--fablepowers-child=1`, the seat's `--model` and `--thinking`, the role prompt from `agents/<seat>.md` with frontmatter stripped, stdin `/dev/null`), with `FABLEPOWERS_PARENT_SESSION`, `FABLEPOWERS_SEAT` and `FABLEPOWERS_PARENT_PID` set. The child loads the gate and cannot dispatch. Child transcripts go to `<parent session dir>/fablepowers-children/<parent id>/` (`$TMPDIR/…` under `--no-session`), linked from the parent with a custom entry. The result is the child's last text, capped at 50 KB, plus a footer and `details` (`seat`, `model`, `usage`, `exitCode`, `childSessionFile`). A pinned seat whose child reports another model or thinking level gets a warning in the result. `cwd` must resolve inside the repository or one of its linked worktrees. On parent shutdown or abort each live child gets SIGTERM, then SIGKILL after 5 s; each child also polls its parent every 2 s and exits when the parent is gone.
- **The approval gate works on Pi.** `approval_gate.py` gains a branch keyed on `harness: "pi"`; the extension resolves `write`/`edit` paths as Pi's tools do (`@`, `~`, `file://`), rewrites the call to that absolute path and sends it to the gate.
  - **Pending:** a root session's `write` that creates `docs/specs/<name>.md` (existence recorded at `tool_call`, the result not an error). The notice is appended to the tool result the model sees.
  - **Denied while pending:** `fablepowers_dispatch` for any seat but `reviewer`; the example's `subagent` tool whatever its agent; `write`/`edit` outside `docs/specs/`, `docs/plans/` and `.fablepowers/`, or with no usable path; Pi config (`.pi/` anywhere, `$PI_CODING_AGENT_DIR`, `fablepowers/models.toml`); and the plugin root. Reads are never gated.
  - **Always denied:** marker edits.
  - **Fails open:** only the gate's explicit deny blocks. Every handler is wrapped to fail open and log, because Pi treats a throwing handler as a block. Gate calls time out after 2 s.
- **Approval on Pi.** Two paths, main session only:
  - the `fablepowers_ask_approval` tool, which asks the gate what is pending and shows the user an Approve / Changes needed dialog (one entry per design when several are pending) in the TUI or over RPC, then records the user's answer inside the tool after the gate re-checks it; in print mode it shows nothing and says to ask for the command;
  - `/fablepowers:approve [key]` and `/fablepowers:withdraw [key]`, extension commands that work in the TUI and in print mode (`pi -c -p '/fablepowers:approve'`). The answer reaches the model as a `fablepowers-result` message and the user as a notification, or one stderr line in print and json mode.

  Both are refused in a dispatched child, and whenever `PI_SESSION_ID` is set, in every mode including the TUI: Pi's shell tool exports it, so a command the model forges through its shell (even a TUI given a pty with `script`) records nothing. Approve from a Pi started in your own terminal, not from inside another Pi's shell.
- **Pi reference.** `skills/workflow/references/pi.md` covers install, the actions-to-tools mapping, wrapper names, seats and the `[pi]` grammar, dispatch (sequential, child transcripts, model-mismatch warning, kill and watchdog), the bootstrap, the approval mechanism and refusal rules, requirements, accepted gaps and session logs. The workflow map and design-spec name Pi's approve command and dispatch tool; the Claude Code injected context stays under 6,000 characters, and a test caps the Pi additions to the shared map at 120 characters.
- **Accepted gaps on Pi**, documented in the reference: shell writes; `env -u PI_SESSION_ID pi -c -p '/fablepowers:approve'` (deliberate evasion); launchers that don't set `PI_SESSION_ID`; edits to the installed plugin while no design is pending; third-party dispatch packages; MCP and code-mode writes; and a print-mode parent killed by SIGINT or SIGKILL, whose children exit only when their watchdog next polls.
- **Tests.** New: `tests/pi/run.sh` (`node --test`; skips without node), extension tests against a faked Pi API and a fake child `pi` (`tests/pi/fake-pi.mjs`), integration tests through the real gate and session-start, and real Pi 1.2.0 payloads under `tests/pi/fixtures/`. Pi sections were added to the approval-gate and session-start suites, plus the all-harness case-variant sections. The OpenCode packaging test now expects `pi/` in the npm tarball.

## 0.6.0 — 2026-10-16

fablepowers runs in OpenCode 2.x from the same repository, with the same skills, seats, approval gate and workflow map. Claude Code and Codex behaviour is unchanged. Tested with OpenCode 2.0.29. Reasons and spike evidence are in `docs/rationale.md` (Decisions 2026-10-16: the OpenCode port).

- **Installs on OpenCode as a plugin.** Add `"plugins": ["fablepowers@git+https://github.com/phelanous/fablepowers.git"]` (optionally `#v0.6.0`) to `~/.config/opencode/opencode.json` or a project's `opencode.json` or `.opencode/opencode.json`. Then restart OpenCode, including its background service. A root `package.json` (`type: module`, `main: opencode/index.js`, a `files` list) makes the repo installable from git. A root `index.js` re-export serves the local-directory form, which ignores `main`. The plugin uses `node:` builtins only.
- **The plugin is an adapter.** `opencode/index.js` registers every skill except approve and withdraw as `fablepowers:<name>`. It registers the three seats as subagents: `fablepowers-implementer`, `fablepowers-strict-implementer` and `fablepowers-reviewer`. Each has its role prompt (the body of `agents/<seat>.md`) inlined in its system prompt and sub-spawns denied; seats get no `external_directory` grant. The plugin also registers the `/fablepowers:approve` and `/fablepowers:withdraw` commands, injects the bootstrap, and turns OpenCode's events into gate payloads. Every gate decision is still made by `hooks/approval_gate.py`, and the seat table is still parsed by `hooks/session-start`. All plugin state is per instance, because OpenCode keeps one plugin instance per directory in one server process.
- **Bootstrap on OpenCode.** It is prepended to the first user message of each root session, re-added after compaction, never doubled, and skipped for child sessions. It holds a preamble naming OpenCode, `references/opencode.md` and the plugin root, then the seat table and its warnings, then the workflow map. It comes from the new `hooks/session-start --opencode` mode, which never reads stdin and prints JSON: `context`, `seats` and `warnings`. It runs once when the plugin loads (3 s timeout). Without python, the bootstrap's first line says the gate is disabled. Without bash, or when session-start fails, a `bootstrap unavailable` line comes first, followed by the map with no seat table.
- **Seats are pinned per user in `[opencode]`.** The table lives in `${XDG_CONFIG_HOME:-~/.config}/fablepowers/models.toml`. Keys are `implementer`, `strict_implementer` and `reviewer`. A value is `provider/model[#variant]`, up to 128 characters; the variant goes to the agent's `model.variant`. An effort key warns and is ignored. An unset or invalid seat runs on the session model, and one warning line names the unpinned seats. The table is read when the plugin loads, so a change needs an OpenCode restart. A pinned seat's per-dispatch `model` argument is stripped. `[codex]` keeps its 0.5.0 grammar and output byte for byte, and each mode ignores the other's table.
- **The approval gate works on OpenCode.** `approval_gate.py` gains a branch keyed on `harness: "opencode"`.
  - **Pending:** a root session's `write` creating `docs/specs/<name>.md` (`existed: false`), an `edit` with an `added` file, a `patch` add whose target the plugin found missing before the call (matched as written or by real path), or a `patch` update with `*** Move to: docs/specs/<name>.md`, as on Codex. Paths are resolved against the session directory, then the git toplevel. The notice is appended to the tool result the model sees.
  - **Denied while pending,** via `permission.evaluate` (with a second check in `tool.execute.before` for dispatch): a `subagent` dispatch to anything but `fablepowers-reviewer` or `explore`, judged by the agent that will actually run, continuations included. Also denied: edits outside `docs/specs/`, `docs/plans/` and `.fablepowers/`; OpenCode config (`opencode.json`/`.jsonc` anywhere, `.opencode/`, the config homes' `opencode/` and `fablepowers/models.toml`); and the plugin root.
  - **Always denied:** marker edits.
  - **Fails open:** the adapter only ever sets `effect = "deny"`. Every hook body is wrapped to fail open, because OpenCode fails a tool or a turn when a hook throws. Gate calls time out after 2 s; failures are logged to `.fablepowers/gate.log`.
- **Approval on OpenCode.** There are three ways:
  - answering **Approve** to design-spec's question in the TUI: exactly one question, exact labels, exactly one pending design;
  - `/fablepowers:approve [key]` typed in the TUI, which runs the plugin command and posts the gate's answer as a message;
  - the same text as the whole message of the main session in `opencode run`, which does not route slash commands. One wrapping pair of quotes is stripped, and the answer is appended to the message.

  `/fablepowers:withdraw [key]` works the same way. Approvals record only from a session positively known to be root. A subagent session or a failed lookup gets a "recorded nothing" answer, while pending creation still treats an unknown session as root. An approval's answer names the next step (`fablepowers:implementation-plan`).
- **Gate path comparisons on OpenCode** are per component and case-insensitive, with NTFS normalisation, for markers, config homes, `models.toml` and the plugin root.
- **OpenCode reference.** `skills/workflow/references/opencode.md` maps the skills' actions to OpenCode tools: `skill`, `subagent` with a seat agent, `question`, and no todo tool. It also covers seats and `models.toml`, the dispatch convention (including continuation, which switches a child's agent), the bootstrap, the approval mechanism and its differences from Claude Code, requirements, testing with `--standalone`, accepted gaps, and where session logs live. The workflow map and design-spec name the OpenCode approve command. The Claude Code injected context stays under 6,000 characters.
- **Requirements.** Python 3.8+ for the gate and bash for the seat table. The plugin finds them the way the launcher does: `FABLEPOWERS_PYTHON` / `FABLEPOWERS_BASH`, then PATH, then absolute fallbacks. It sees the OpenCode server's environment, so set these where the background service starts.
- **Accepted gaps on OpenCode**, documented in the reference:
  - shell writes;
  - self-approval by the model through the shell (`opencode run -s … /fablepowers:approve`) or the server API;
  - edits to the installed plugin while no design is pending;
  - config in locations the guard doesn't list;
  - another plugin's permission hook overriding a deny.

  The Codex reference also records the custom `CODEX_HOME` guard-parity gap: only that home's `config.toml` is guarded, and it is compared exactly.
- **Tests.** New: `tests/opencode/run.sh` (`node --test`; skips without node), plugin tests against a fake `ctx` built from real OpenCode 2.0.29 payloads (`tests/opencode/fixtures/`), and integration tests that run the real gate and session-start for each payload type. OpenCode sections were added to the approval-gate and session-start suites. A version-parity check covers `package.json`, both `.claude-plugin` manifests and the CHANGELOG head.

## 0.5.0 — 2026-10-15

fablepowers runs in OpenAI Codex (CLI and app) from the same repository: same skills, seats, approval gate and workflow map. Claude Code behaviour is unchanged. Tested with Codex CLI 0.162.1. Reasons and spike evidence in `docs/rationale.md` (Decisions 2026-10-15: the Codex port).

- **Installs on Codex as-is.** `codex plugin marketplace add phelanous/fablepowers`, then `codex plugin add fablepowers@fablepowers`; Codex reads the existing `.claude-plugin/` manifests and `hooks/hooks.json`, so no `.codex-plugin/` manifest is added. The hooks run once trusted in `/hooks`, and again after an update that changes `hooks.json`; a 0.4.0 install keeps its eight trusted entries and adds three.
- **The session-start hook detects Codex and injects the seat table.** Detection reads the hook payload's `transcript_path` (a `rollout-*.jsonl`, or a path under `.codex/sessions/` or `$CODEX_HOME/sessions/`), else `PLUGIN_ROOT` equal to `CLAUDE_PLUGIN_ROOT`. From the environment, detection reads only `CODEX_HOME` (for that path rule), `PLUGIN_ROOT` and `CLAUDE_PLUGIN_ROOT`; other variables Codex leaks from its launcher decide nothing. `model` and `permission_mode` decide nothing: Claude Code's compact SessionStart carries `model` too. On Codex the preamble names the harness, points to the Codex reference and the plugin root, and lists each seat's model and reasoning effort, followed by the workflow map; at most 8,000 characters. On Claude Code (empty stdin or Claude's payload) the hook behaves exactly as in 0.4.0.
- **Seat models are configurable per user.** Defaults: implementer and reviewer `gpt-6.1-sol` (high), strict implementer `gpt-5.6-terra` (medium); Sol needs Sol access, and its id comes from the Codex binary's catalog. `${XDG_CONFIG_HOME:-~/.config}/fablepowers/models.toml`, `[codex]` table, overrides any seat; a bad entry falls back to its default with a warning in the injected context (at most three lines). If a seat's model is unavailable, the orchestrator stops and points to the file instead of retrying without a model.
- **The approval gate works on Codex.** A spec added with `apply_patch` under `docs/specs/`, or moved there with `Move to:` (confirmed by the tool's response, main session only, paths from the session's working directory), marks the design pending. While pending, every spawn except a fablepowers reviewer (v2 task name `fablepowers_reviewer_*`, v1 first line `fablepowers-seat: reviewer`) is denied, and so is any `apply_patch` with a repository path outside `docs/specs/`, `docs/plans/` and `.fablepowers/` (one bad path denies the whole patch) or touching Codex config (`.codex/config.toml`, `rules/`, `agents/`, `hooks*`, `$CODEX_HOME/config.toml`). Patches to markers are denied always. A patch the gate cannot parse fails closed while a design is pending.
- **Approval on Codex is a typed command.** `$fablepowers:approve [key]` or `$fablepowers:withdraw [key]` as the user's whole message, from the main session only; there is no question path. The hook answers through context the model relays, since Codex shows hook warnings and block reasons to neither the model nor `codex exec` users. The approve and withdraw skills carry `agents/openai.yaml` with `allow_implicit_invocation: false`, and their bodies gain a Codex branch that never treats a missing gate answer as approval. A message that starts with `$fablepowers:approve` or `$fablepowers:withdraw` but is not the command records nothing and gets an answer: a single trailing word is read as the key, so an unknown one gets "no pending design matches" with the pending keys; anything else gets "not recognised", asking for the command on its own. Every Codex deny ends with the recovery line: trust the hooks in `/hooks`, or set `FABLEPOWERS_GATE=off`.
- **Patch paths read as Codex reads them; control characters fail closed.** The gate splits a patch on `\n` only, as Codex does, and takes a header path untrimmed after its `: `, so a `\v`, `\f`, `\x1c`–`\x1e`, `\x85`, U+2028 or U+2029 inside a header no longer hides the rest of its path. A header path holding a control character (or one the gate cannot resolve) no longer lets the whole patch through: it is denied while a design is pending, and always when it could name a marker, by its text or through a symlink.
- **No-python warning reaches Codex.** Without python the launcher's "gate disabled" warning also goes out as `additionalContext` on Codex's PostToolUse `apply_patch` and `UserPromptSubmit`, so the model relays it. A Codex PreToolUse can carry only the `systemMessage`, which nobody sees, and a subagent's event (with `agent_id`; v2 subagents share the root's session) sends its context to the subagent only, so neither uses up the once-per-session warning: the main session's next event that can carry context still warns.
- **Dispatch by reference on Codex.** The Codex reference (`skills/workflow/references/codex.md`) maps the skills' actions to Codex: skills read from their `SKILL.md`, seats spawned with the seat table's model and effort, no context fork, a task name `fablepowers_<seat>_<suffix>` (v2) and a first line `fablepowers-seat: <seat>` naming `agents/<seat>.md` as the role prompt, for both multi-agent tool generations. It also covers the approval mechanism and its differences from Claude Code, the rules file, hook trust, accepted gaps and where session logs live.
- **Commits through an opt-in rules file.** `codex/rules/fablepowers.rules` allows plain `git add`, `git commit` and `git worktree add` in the sandbox; copy it to a trusted project's `.codex/rules/` or to `~/.codex/rules/`. Without it each git write asks for approval. Project rules need the project's trust entry in `~/.codex/config.toml` (Codex writes it on the first trusted session); a `-c` trust override is not honoured for them on `codex exec resume`.
- **A trust helper for headless runs.** `scripts/codex-hook-trust.sh [plugin@marketplace] [cwd]` asks `codex app-server` for the plugin's hooks and prints a one-run `-c hooks.state=…` override; it never writes config. On an error it prints nothing on stdout and exits 1, so headless scripts check its status (`trust="$(…)" || exit 1`).
- **Harness-neutral approval wording.** The workflow map and design-spec's closing line name each harness's approve command (`/fablepowers:approve` or the Approve answer on Claude Code, `$fablepowers:approve` on Codex); a harness with no blocking question asks in plain text and ends the turn. The Claude Code injected context stays under 6,000 characters.
- **Accepted gaps on Codex**, documented in the reference: shell writes (including an `apply_patch` heredoc run through the shell, which Codex reports as a Bash call with no PostToolUse), a spawn mislabelled as a reviewer, re-tasking an allowed agent through follow-up or send-message, the rest of `~/.codex` and the installed plugin's own scripts in the plugin cache (the config guard covers only the config paths above), and approvals picked from the Codex app's skill menu, which the hook cannot see.

## 0.4.0 — 2026-10-15

The design-approval checkpoint becomes mechanical on Claude Code, and the skills stop naming Claude Code tools so other harnesses can follow. Reasons in `docs/rationale.md` (Decisions 2026-10-15).

- **A hook enforces design approval.** Creating a new spec under `docs/specs/` marks the design pending. While any design is pending, dispatching `fablepowers:implementer` or `fablepowers:strict-implementer`, and editing files outside `docs/specs/`, `docs/plans/` and `.fablepowers/`, are denied with a message telling the model to stop and ask. Reviewer dispatch, spec and plan edits, and paths outside the repository stay open; paths are resolved through symlinks and `..` first. Once approved, the gate is quiet for that design.
- **Only the user can approve.** Two paths: answering Approve to the design question (exact options Approve / Changes needed, one design pending), or the user-only `/fablepowers:approve [key]`; with several designs pending the command needs a key and otherwise lists them and records nothing. When an Approve answer can't be recorded, the hook says why and which command to run. `/fablepowers:withdraw [key]` drops an abandoned design. Both commands set `disable-model-invocation: true`, so the model can't run them, and a test asserts it.
- **Markers can't be forged through the edit tools.** `.fablepowers/<key>/pending` and `approved` are written by the hook; an edit-tool write through any `pending`/`approved` path under `.fablepowers` is always denied, compared case-insensitively and as NTFS resolves names (trailing dots and spaces, `:stream` suffixes). An `approved` that isn't a regular file holding the gate's JSON doesn't count and is logged. On approval, `pending` stays as the audit record.
- **The gate fails open, visibly.** It needs Python 3.8+ (`FABLEPOWERS_PYTHON` overrides the interpreter); without one it allows everything and shows a warning once per session: on any hooked call in a repository that has a `.fablepowers/`, and in any other repository on the calls where the gate would have acted (a spec created under `docs/specs/`, the approval question, `/fablepowers:approve` or `/fablepowers:withdraw`). Other calls, and everything outside git, stay silent. `FABLEPOWERS_GATE=off` disables blocking and logs what it would have blocked to `.fablepowers/gate.log`; malformed payloads allow and are logged there too. Tested with Claude Code 2.1.299, now the stated minimum.
- **Settings files are closed to the edit tools while a design is pending.** Write, Edit, MultiEdit and NotebookEdit on any `.claude/settings.json` or `.claude/settings.local.json` (the repo, `~/.claude`, anywhere) are denied with a reason naming the pending design and saying the user can make the change themselves. This closes the usual settings files, not every way to register a hook: edit-tool writes to the installed plugin's own hook files, to a config directory not named `.claude`, or to managed settings are not blocked (see the accepted gap below).
- **Accepted gap: shell writes and other hook locations.** The gate watches the edit tools and dispatch, not shell commands, so markers, specs and a settings hook that auto-answers the question can still be written through the shell. The edit tools can still reach the installed plugin's hook files and config directories other than `.claude`, guarded only by Claude Code's permission prompt for paths outside the project. Both are adversarial paths, outside the gate's threat model. design-spec creates the spec with the file-write tool for this reason: a spec written through the shell is never gated. Documented in the README and the Claude Code reference.
- **Small designs write a short spec file**, so every design that reaches the approval ask is gated. The brief ends with how to approve (answer Approve, or run `/fablepowers:approve`). `docs/specs/` is for designs only.
- **Skills and agent bodies are harness-neutral.** They name actions and seats (implementer, strict implementer, reviewer; frontier or mid tier) instead of tools and models. Plan headers accept `implementer` / `strict-implementer`; `opus` / `sonnet-strict` still work.
- **A Claude Code harness reference** (`skills/workflow/references/claude-code.md`) maps those actions to tools, seats to agents and models, and documents the bootstrap, the approval mechanism, the report-name write guard and where session logs live. The session-start preamble names Claude Code and keeps the Skill / Agent / `subagent_type` mapping in the injected context, so dispatch behaves as before; the injected context stays at or under 6,000 characters, and a test asserts it.

## 0.3.0 — 2026-10-09

Workflow ideas from superpowers v6–v7 that fit this plugin's evidence, adapted rather than vendored. Reasons, and the upstream ideas left out, in `docs/rationale.md`.

- **Agents can't spawn agents.** `implementer`, `strict-implementer` and `reviewer` have `disallowedTools: Agent`; a sub-spawn would run on the parent's inherited model, the defect pinned agents exist to fix.
- **Implementers are dispatched by reference.** The dispatch names the plan path, task heading and spec path; the implementer reads its task from the plan. Strict-tier dispatches still carry the task inline.
- **Reports go to files; returns are short.** Implementers and reviewers write the full report to a path the dispatch names and return at most 15 lines. With no path given, or when the harness refuses the write (it refuses generic names such as `report.md`, so the workspace uses specific ones), the full report comes back inline.
- **Handoff files live in `.fablepowers/<plan>/`.** A per-plan workspace at the worktree's top level holds reports, review packages and the ledger. It ignores itself, leaves a repo's own `.fablepowers/.gitignore` alone, and is safe to delete after merge. Work with no plan keys it on the spec file, or on `@<branch-name>` when there is no spec either (`/` becomes `-`; names starting with `.` and `@` plus an existing `.md` file are refused).
- **A progress ledger makes resume safe.** The orchestrator appends one line per checked task, and one per integration review and fix round, to `progress.md`; after compaction or in a new session it reconciles the ledger with `git log`, never re-dispatches a committed task, runs the pending checks of a commit that has no ledger line yet, and counts re-reviews against the cap, so the fix after the second re-review goes to `fablepowers:verify-done`, not a third review. The workflow map points a resumed session to `fablepowers:subagent-execution`, since compaction re-injects only the map.
- **Integration review diffs from the merge-base.** A new `review-package` script writes the commit list, `--stat` and diff from `git merge-base <base> HEAD`, so base-side commits no longer show up as phantom deletions. Empty ranges and unrelated histories exit 3.
- **The orchestrator doesn't coach reviewers.** Dispatches never carry a pre-rated severity, an instruction to ignore something, or the implementer's rationale; a stated rationale never lowers a finding's severity, and a defect the plan mandates is still reported, flagged plan-mandated.
- **Reviewers list what they declined to judge, and the orchestrator rules on each.** The final report to the user gains a phone-readable **Rulings I made** section: declined-to-judge items, capped re-review leftovers, plan conflicts resolved, plan-mandated defects kept.
- **Reviewers judge spec silence by what a reasonable user would expect**, and never run `checkout`, `reset`, `stash` or similar in the shared tree; other revisions go in a throwaway worktree.
- **Plans carry a Review Focus section**: up to five spec-implied inputs no task tests yet, each assigned to the owning task; plan review checks it.
- **Design asks who owns the how.** `design-spec` asks which platform, language and library choices the user wants to make; defaults go under "Decisions I made".
- **Substantial specs get a builder check.** A fresh reviewer reads the spec as its builder and lists what it would have to guess; the build-changing questions reach the user in one round before the approval brief.
- **`behavioral-testing` names three more anti-patterns:** mirror assertions, change detectors, and the string-presence trap.
- **The SessionStart hook works with a broken `PATH` wherever bash is at `$BASH` or a standard absolute location.** The `hooks.json` command picks bash with sh builtins only — `$BASH`, then `/bin/bash`, `/usr/bin/bash`, `/usr/local/bin/bash`, `/opt/homebrew/bin/bash`, and a PATH lookup only if none exists — and the script uses only bash builtins; 0.2.x failed with `env: 'bash': No such file`. Output is unchanged. Tested through `/bin/sh -c` and `/bin/bash -c`, and through a non-bash sh with `BASH` unset (dash where installed, otherwise zsh in sh emulation), each under a normal and an empty `PATH`. The hook and `review-package` each ship a test suite.

The three vendored skills are re-based on superpowers v7.0.0, picking up fixes upstream had already made.

- **`systematic-debugging` no longer triggers extended thinking.** The skill text contained the trigger keyword, so every session that loaded it paid for extended thinking.

- **Pull requests work on Forgejo and GitLab.** Finishing names non-interactive `gh`, `fj` and `glab` commands, checks auth first, and falls back to the URL the forge printed on push.

- **Finishing never removes worktrees it doesn't own.** Only worktrees under the project root's `.worktrees/` or `worktrees/` are cleaned up; host-owned ones such as `.claude/worktrees/` are left alone, and a refused removal is reported instead of forced.
- **Discarding work is offered only when asked for.** It is no longer an item in the standard menu.
- **`using-git-worktrees` doesn't nest worktrees.** It detects an existing linked worktree (including inside submodules), prefers the harness's native worktree tool, and places new worktrees under the project root instead of a global directory.

## 0.2.0 — 2026-09-24

From the second log audit (40 sessions on 0.1.0; full numbers in `docs/rationale.md`).

- **A design brief precedes the approval ask.** `design-spec` ends with a phone-readable brief under six fixed headings (What changes, Decisions I made, Not doing, Risk, Open the spec if, Verified by), then one question with exactly two options, Approve and Changes needed. 16 of 42 approval asks under 0.1.0 had no design summary in the turn; design variants had moved into the options.

## 0.1.0 — 2026-09-07

First release. Packages the personal superpowers fork as an installable plugin.

**Contents**

- Seven forked skills: `workflow`, `design-spec`, `implementation-plan`, `subagent-execution`, `behavioral-testing`, `integration-review`, `verify-done`.
- Three skills vendored from superpowers 5.0.7 (MIT, Jesse Vincent; see `NOTICE`) with cross-references retargeted: `systematic-debugging`, `using-git-worktrees`, `finishing-a-development-branch`.
- Three agents with pinned models: `implementer` (Opus), `strict-implementer` (Sonnet), `reviewer` (Opus).
- A SessionStart hook that loads the workflow map, replacing the CLAUDE.md preamble the fork previously needed.
- `docs/rationale.md` (the evidence) and `scripts/analyze_delegation.py` (the measurement harness).

**Design decisions from the 2026-09-07 log audit** (27 fork-era sessions; full numbers in `docs/rationale.md`)

- **Roles become agents with pinned models.** `model` was unset on 101 of 114 `Agent` spawns, so subagents silently inherited the orchestrator's model and effort. The model now lives in the agent definition, not in whatever prompt gets written at dispatch time.
- **The orchestrator never implements a plan task.** Its model produced 97% of fork-era output tokens — 78% in the main loop itself, the rest in subagents that inherited its model; 9 of 13 plan headers read "Implementer tier: frontier (orchestrator implements directly)". The tier wording invited it, so the tier wording is gone. The only code the orchestrator writes itself is a one-line fix inside a review loop, and it says so.
- **The design-approval ask stands alone.** The checkpoint held in 17 of 19 sessions; both misses had the same shape — the approval question bundled with an open design question. The ask is now its own single-question call or its own message, and an answer that picks an option is never approval.
- **Integration re-reviews are capped at two rounds.** The gate earns its cost (~10 of 18 first passes found a blocker), but one feature ran six re-review rounds. After the cap, remaining must-fix items are fixed, `fablepowers:verify-done` runs, and the report to the user states that the loop was capped and what remained.
